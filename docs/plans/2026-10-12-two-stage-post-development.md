# 两阶段模型后期独立阶段实施方案

> For agentic workers: use superpowers:executing-plans only when the user explicitly starts this separate phase. **方案已确认，当前禁止执行。前五组完成后必须先汇报并停止，不能自动执行本文。** 下方 prompt 仅供用户以后单独启动本阶段时使用。

**Goal:** 在开发研究完成后，单独验证唯一候选的部署兼容性及7月后期表现。

**Architecture:** 先在开发期固定配置回放无新标签模式，再正式冻结配方、方向档位、实现和评价；之后在7月分别运行按日更新与冻结参数两种模式。所有已训练对照遵守对应模式，结果分别解释。

**Tech Stack:** 沿用项目 Python、pandas、numpy、scikit-learn 环境，CPU，既有模型与关键统计存储框架。

**Spec:** [前五组实施方案](2026-10-12-two-stage-implementation.md)、[完整研究路线](../research_plan_two_stage.md)、[决策记录](../research_decisions.md)第42节，以及用户2026-10-12“这部分计划在完成这一阶段后单独实行，不要在执行完前面步骤后自动实施”。

## 执行边界

- 启动必须同时满足：前五组已完成阶段汇报，以及用户之后明确要求启动本后期独立阶段。通过测试、开发指标良好、前五组全部完成或计划已被认可，都不构成自动启动条件。
- 边界覆盖本文全部工作，包括仅使用4–6月的冻结参数部署兼容性回放、正式模型冻结、7月数据读取/拟合/预测/评分及7月不确定性分析。
- 当前只保存设计；不建立后台任务、排程或自动后续步骤。不把本文件串入前五组默认运行入口。
- 前五组保留的是开发候选和可复现来源；正式冻结文件、部署模式回放及7月分析均属于本独立阶段。
- 未来单独启动本阶段不等于授权真实部署、调整收费或提交到外部系统；本计划仅包含离线兼容性和后期评价。

## 1. 启动时检查开发交付

读取前五组阶段报告，确认唯一候选、对照、合同/信号/收缩/消融的实际贡献、稳定性证据和未解决问题。所有拟主张正向增量的良好分支应已接受第五组验证；不把多个开发候选带到7月重新择优。

若没有候选满足已确认的相对H0增量与风险条件，报告无合格候选；不为产生后期赢家临时扩大搜索，也不无条件开启7月。0.5%近似并列门槛仍未启用，不能借本阶段追加。

## 2. 先做开发期部署兼容性回放

模型配方、超参数和方向档位沿用开发阶段候选，不为部署模式单开调参。4、5、6月分别在月初 D 用 `[D−30天,D)` 创建且 `closedAt<D` 的合法历史拟合一次，整月冻结回归系数、标准化参数及其他学习得到的状态；新订单及创建前市场特征继续更新，但当月新结算标签不进入模型。

候选、H0、方向×期限均值遵守相同冻结方式；Base直接使用原字段。同一批开发评分订单与既有日更新结果配对，检查优势有多少依赖新标签反馈。若冻结模式明显薄弱，明确记录适用条件；不等待7月后才把成绩较好的模式改称主结果。

这一步也属于后期独立阶段，不能因为仅读4–6月就提前自动运行。

## 3. 正式冻结

在读取7月之前保存 `model_freeze.json` 及必要来源。至少包括：

- 唯一候选配方、概率/金额模型、特征定义、正则、Put/Call档位。
- 30天训练窗口、UTC日更新时点、严格结算可用条件、数据不足与数值失败回退。
- 预处理版本、原v1订单资格、Base共同口径、时间边界和单位换算。
- 对照清单、两种模式及其预定角色、指标/风险条件/统计设置/结果解释规则。
- 代码内容摘要、依赖版本、随机种子、开发期输入来源和截止时间。
- 无新标签模式所需的单份初始模型/系数和标准化参数；不保存不必要的逐日模型副本。

冻结的是算法和选择规则；日更新模式仍按锁定流程拟合新系数。不能根据7月成绩换特征、参数、方向档位或对照。预定样本不足回退可以触发，但不能按测试误差临时决定回退。

## 4. 7月的两种固定模式

区间固定为UTC `[2026-07-01T00:00:00Z,2026-07-31T17:11:48Z)`。沿用原v1有效订单、Base共同评分名单及结算截止，不重划分或补回此前排除的边界订单。7月此前看过描述统计，称内部后期测试，不称完全盲测。

| 项目 | 按日更新 | 冻结参数 |
|---|---|---|
| 角色 | 有结算反馈条件下的研究评价 | 无新标签条件下的部署证据 |
| 拟合 | 每天D用此前30天合法已结算订单 | 7月开始前拟合一次 |
| 系数、标准化等学习状态 | 每天更新 | 整个测试期保持不变 |
| 7月新结算标签 | 仅在以后日期、满足历史条件后使用 | 仅供评价端，模型完全不可使用 |
| 创建时可得的Base/合同/行情特征 | 逐订单更新 | 同样逐订单更新 |
| 模型结构与方向档位 | 固定 | 固定 |

固定评价官方Base、原H0、方向×期限均值、唯一候选。需要估参的对照在各模式使用同样的训练/冻结条件，不把每日更新候选与冻结H0作主要比较。

两模式共用评分名单及尾部分组。历史q90分组由隔离评价端按原历史规则构造，只供诊断，不向无反馈模型传递新标签信息。先生成预测再评价，不依据某笔实际赔付决定预测方式。

## 5. 指标、结论及失败处理

- 每个模式分别检查整体RMSE低于同模式H0、MAE不高于H0，以及已确认的Base方向风险条件与整体金额偏差；同时列简单均值对照。
- 7月单月主RMSE/MAE等同该月的全订单指标；复用第五组配对时间块与日期敏感性方法，7月独立计算，不与4–6月混在一起掩盖后期退化。
- 区间跨0但点估计/风险条件通过时，记录后期点估计支持改善、增益仍不确定。尾部支持度不足时记录证据不足，不能根据测试分组重新选lambda或把缺证据当通过。
- 日更新通过、冻结参数不通过，只支持有反馈条件的用途；冻结模式较好而日更新失败，也应分别报告，不能事后更换主要研究模式来宣称整体成功。
- 原定模式未通过则如实记录后期失败，不增加候选、调整门槛或重复使用7月选参。
- 若确认实现错误，可以修复并重跑同一锁定研究方案；保留错误、修改、前后结果和重跑记录，不借修复更改模型设计，也不将看过结果后的修复版本包装为完全独立的首次测试。

## 6. 离线部署检查

核查创建时能否提供Base、订单字段与历史分钟行情，并披露字段时间匹配限制；不能假定官方验证标签会回传。检查缺失输入/异常回退、逐单ID对齐、单位、非负有限输出、批量预测耗时/内存及回退率。

必须用合成测试证明：冻结参数模式隐藏或改变全部后期标签不影响任何预测；日更新模式改变未来标签不影响此前预测；两模式在相同初始训练截止和输入下首日预测一致。评分标签与模型输入分离，7月支持度不足不触发事后改档位。
